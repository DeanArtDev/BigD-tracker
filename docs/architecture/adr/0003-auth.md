# ADR-0001: Session-based аутентификация с sessionId в cookie и Redis

- Статус: Архив (не реализовано)
- Дата: 2026-05-08
- Авторы: <имя>
- Связанные ссылки: <issue / epic / pr / doc>

## Контекст

Необходимо реализовать механизм аутентификации для BFF (NestJS), который обслуживает Next.js приложение и общается с
микросервисами через RabbitMQ. Транспорты на клиенте — HTTP (для SSR из Next.js сервера) и WebSocket (для
query/mutation/subscription из браузера через Apollo + GraphQL).

Требования:

- Клиент не должен иметь доступ к идентификатору сессии из JavaScript.
- BFF должен уметь мгновенно инвалидировать сессию (logout, смена пароля, бан пользователя).
- Решение должно одинаково работать для HTTP и WebSocket.
- Должна быть возможность горизонтально масштабировать BFF (несколько инстансов).
- Истечение сессии должно проверяться периодически, без продления TTL на каждый запрос.

Ограничения:

- BFF — централизованный, общее хранилище состояния доступно.
- Микросервисы не знают о сессиях — им передаётся только `userId`.

## Решение

Используем session-based аутентификацию:

- В cookie хранится только `sessionId` — случайная строка с энтропией не менее 256 бит (`crypto.randomBytes(32)`).
- Cookie настроен как `httpOnly`, `secure`, `sameSite=lax`.
- В Redis по ключу `session:{sessionId}` хранится payload сессии (`userId`, метаданные) с фиксированным TTL (например,
  30 минут — 24 часа в зависимости от чувствительности).
- TTL не продлевается на каждой активности — сессия живёт ровно столько, сколько было задано при создании.
- Проверка сессии при WebSocket: на handshake — обязательно; во время сессии — раз в N минут на следующей операции.
- Мгновенная инвалидация — через Redis Pub/Sub канал `session:invalidated`. Все инстансы BFF подписаны на канал и
  закрывают соответствующие WS-соединения.
- Подписанный токен (JWT или HMAC) не используется — sid с высокой энтропией + проверка наличия записи в Redis даёт
  эквивалентный уровень безопасности.

## Причины выбора

- Мгновенная инвалидация — ключевое требование. Stateless JWT в cookie этого не даёт без blacklist-таблицы, что
  нивелирует преимущества JWT.
- BFF централизованный, общий Redis уже нужен для других задач (кеширование, pub/sub) — отдельная инфраструктура для
  сессий не требуется.
- Подписанный токен в дополнение к sessionId не закрывает ни одной реальной угрозы при условии достаточной энтропии sid:
  подбор математически невозможен, кража cookie ломает обе схемы одинаково, компрометация Redis ломает обе схемы.
- Session payload не утекает на клиент — в cookie только непрозрачный идентификатор.
- Один и тот же механизм работает для HTTP и WebSocket: cookie уходит при handshake автоматически.

## Альтернативы

### 1. JWT в cookie без Redis

Почему не выбрали:

- Невозможно мгновенно инвалидировать токен до истечения exp без blacklist-таблицы.
- Если добавлять blacklist — фактически возвращаемся к session-based, но с раздутым cookie (JWT 500+ байт vs sessionId
  64 байта).
- Payload в JWT попадает на клиент в base64, что неприемлемо для чувствительных данных.
- JWT отправляется при каждом запросе, увеличивая нагрузку на сеть и время обработки.

### 2. SessionId + подписанный токен в cookie

Почему не выбрали:

- Подпись не закрывает ни одну реальную угрозу при достаточной энтропии sid.
- Подделать sid без знания настоящего значения невозможно — энтропия 256 бит делает подбор нереалистичным.
- Дополнительный код, дополнительная сложность, нулевой security gain — security theater.

### 3. Sliding expiration (продление TTL на каждой активности)

Почему не выбрали:

- Бизнес-требование: сессия должна истекать в фиксированное время от создания, а не от последней активности.
- Дополнительная нагрузка на Redis (`EXPIRE` на каждый запрос).
- Сложнее аудит — непонятно, когда сессия реально завершится.

### 4. In-memory сессии в процессе BFF

Почему не выбрали:

- Не работает при горизонтальном масштабировании — sticky sessions усложняют балансировку.
- Перезапуск инстанса = разлогин всех его пользователей.
- Нет общего канала для pub/sub инвалидации между инстансами.

## Последствия

### Плюсы

- Мгновенная инвалидация сессий через Redis Pub/Sub.
- Минимальный размер cookie (только sid).
- Единый механизм для HTTP и WebSocket.
- Горизонтальное масштабирование BFF без sticky sessions.
- Чувствительные данные сессии не покидают серверную часть.
- Простая модель — меньше места для ошибок реализации.

### Минусы

- Зависимость от доступности Redis: при его падении аутентификация не работает.
- На каждой первой WS-операции в окне N минут — поход в Redis (нагрузка).
- Дополнительная инфраструктура (Redis), требующая мониторинга и резервного копирования.
- Если Redis не отвечает, обращение к БД для проверки сессии может стать узким местом, но отказ Redis не сломает систему, 
  а только замедлит её.

### Риски

- Утечка sessionId через XSS — закрывается `httpOnly`, но не на 100% (XSS даёт другие векторы).
    - Митигация: CSP, регулярный аудит, sanitization.
- Компрометация Redis — атакующий получает все активные сессии.
    - Митигация: сетевая изоляция, аутентификация Redis, шифрование at rest.
- Пропущенное pub/sub событие при разрыве связи между инстансом и Redis — пользователь продолжает работать с
  инвалидированной сессией до следующего periodic recheck.
    - Митигация: разумный интервал recheck (1-5 минут), мониторинг подписки.
- CSRF на mutating-запросах через HTTP.
    - Митигация: `sameSite=lax`, при необходимости — отдельный CSRF-токен для критичных операций
    - Проверка сессии в БД

- [ ] Реализовать модуль `SessionService` на BFF: создание, получение, удаление сессии
- [ ] Реализовать создание sessionId (`crypto.randomBytes(32)`) и сохранение в Redis при логине
- [ ] Настроить cookie (`httpOnly`, `secure`, `sameSite=lax`)
- [ ] Адаптировать `AuthGuard` для проверки sessionId на HTTP-запросах
- [ ] Реализовать проверку sessionId на WebSocket handshake (через `connectionParams` / `request.headers.cookie`)
- [ ] Реализовать periodic recheck (раз в N минут на следующей операции через WS)
- [ ] Реализовать Redis Pub/Sub канал `session:invalidated` и подписку в каждом инстансе BFF
- [ ] Реализовать logout: `DEL session:{sid}` + `PUBLISH session:invalidated {sid}`
- [ ] Покрыть тестами: создание, валидация, истечение, инвалидация, переподключение WS
- [ ] Настроить мониторинг: количество активных сессий, hit/miss Redis, latency

## Критерии успеха

- Logout закрывает все активные WS-соединения пользователя в течение секунды.
- Истёкшая сессия гарантированно отклоняется не позже чем через N минут после истечения.
- BFF масштабируется горизонтально — пользователь может попадать на любой инстанс без потери сессии.
- Размер cookie не превышает 200 байт.
- Нагрузка на Redis от проверок сессий приемлема.
- Нет инцидентов с утечкой данных сессии на клиент.
